# 任务：额度刷新改成「自适应频率」+ 面板显示数据新鲜度

## 背景与用户诉求

用户问：「这个刷新额度按钮不应该改成每 60 秒实时刷新吗？」

**当前机制**（已查明）：
- 前端 `setInterval` 每 **5 秒** 拉一次 `/api/status`（读网关本地缓存，免费）
- 后端 `quotaPollIntervalMs = 300000`（**5 分钟**）同步 CC 上游
- 一次 `refreshAll()` = 每个账号 **4 个** CC 接口
  （`/alpha/whoami`、`/alpha/billing/credits`、`/alpha/billing/subscriptions`、`/alpha/usage/summary`）
- 实测单次刷新耗时 **3.38 秒**
- 手动刷新按钮 → `POST /api/accounts/refresh`，匿名限流 `PUBLIC_REFRESH_MIN_MS = 5000`
- 额度耗尽时已事件驱动重查（`src/proxy.mjs:389`）

**为什么不能无脑改成 60 秒**：60s × 4 接口 = 每账号每天 5,760 次请求，
多账号成倍放大 → 容易被 CC 侧风控识别为爬虫。
且 5h/周/月窗口值本身变化很慢，60 秒轮询大部分是无效开销。

## 目标方案

### 一、自适应轮询（替代固定 5 分钟）

后端维护「最近活动时间」，动态决定下一次同步间隔：

| 条件 | 间隔 |
|---|---|
| 最近 **5 分钟**内有代理请求（说明正在用） | **60 秒** |
| 空闲（5 分钟无请求） | **300 秒**（保持现值） |

**实现要点**：
- 在 `src/proxy.mjs` 成功/失败代理请求后，调用一个 `touchActivity()` 回调
  （与现有 `refreshAccount` 回调同风格传入，别破坏现有签名）
- 用**单个可变定时器**（`setTimeout` 自调度）而非两个 `setInterval`：
  每次执行完根据「距上次活动多久」决定下次延迟，避免定时器打架
- 新增配置项（`src/config.mjs` + `config.json` + `config.example.json`）：
  ```
  quotaPollIntervalMs: 300000        // 保留：空闲间隔
  quotaActivePollIntervalMs: 60000   // 新增：活跃间隔
  quotaActiveWindowMs: 300000        // 新增：判定“活跃”的时间窗（5 分钟）
  ```
- **必须保留**「设 0 可关闭轮询」的语义（`quotaPollIntervalMs: 0` → 完全关闭定时器，
  测试可能依赖这个）。若 `quotaActivePollIntervalMs` 为 0，则退化为纯空闲间隔
- 定时器仍要 `unref()`，不要阻止进程退出
- **活跃态并发保护**：如果上一轮 `refreshAll()` 还没跑完，跳过本轮，别叠起来

### 二、面板显示数据新鲜度（解决「感觉数据是死的」）

前台面板要让人一眼看出**数据有多新**，而不是猜。

- 每个账号显示该账号额度快照的时间：`fetchedAt`（已有字段）
  → 渲染成相对时间：**「额度更新于 12 秒前」/「3 分钟前」/「刚刚」**
- 相对时间**每秒本地重算**（不额外请求），超过 10 分钟显示绝对时间（`21:05:16`）
- 快照过旧时（> 2 倍空闲间隔，即 > 10 分钟）用 `--warning` 色提示
- 「刷新额度」按钮：
  - 点击后进入 **loading 态**（转圈动画 + 禁用），实测耗时 ~3.4 秒，不能让用户以为没反应
  - 完成后**短暂显示「已刷新」**反馈（1.5 秒后恢复）
  - 被服务端节流时（响应 `throttled: true`）显示「刚刚已刷新过」，**不要报错**

### 三、不要动的东西

- 前端 5 秒本地轮询保持不变（那是免费的，且让本地统计实时）
- `PUBLIC_REFRESH_MIN_MS` 节流保持不变
- 事件驱动的额度耗尽重查保持不变
